# Kits suite admin screens: UX/UI audit

Scope: the React (Kits Core shell) and PHP-fallback admin screens of Kits Core, DirectoryWeb, RankWeb, InsightWeb, SourceWeb, MailWeb and PlanWeb, built from the `commercial` track zips in `dist/` and served in WordPress Playground (WordPress 7.1.5, PHP 8.2).
Date: 2026-11-28. Viewports: 1280 x 900 and 375 x 812 (emulated mobile). Account: administrator, signed in by a temporary must-use plugin kept outside the repo (no password was typed).
Judged against: WCAG 2.2 (success criteria cited per finding), Nielsen's heuristics, and the suite's own copy (the screens are compared with each other and with their own help text). No house design-system document was consulted, so none is cited.

Method and limits, stated plainly:

- Probes run: `probe-core.js` (contrast, tap targets, names, overflow, outline) on every screen listed in section 1, and `probe-focus.js` after a real Tab keypress on a sample of controls. I did **not** run `probe-heuristics.js`, `probe-perception.js`, `probe-ltr.js`, `probe-rtl.js`, `probe-parity.js` or `probe-routes.js`. The plural and copy findings come from the reading pass, not from `probe-ltr.js`. The suite is English only, so RTL and parity were not applicable.
- `probe-core` reports the WordPress admin chrome (menu, admin bar, footer) too. I filtered those selectors out and also dropped two probe artefacts: `screen-reader-text` spans (clipped, not visible) and the hidden `tabindex=-1` inputs behind DataViews checkboxes (the visible `role=checkbox` span carries the `aria-label`).
- Seeded demo data (neutral): 5 PlanWeb entries (2 of 7 attempted were rejected by the form validation and not retried), 3 DirectoryWeb listings, 4 countries x 20 days of Search Console country rows for InsightWeb, 4 Email Log lines with 2 held queue rows. The InsightWeb totals tiles stay at 0 because I seeded only the country rows, not the site-total metric the tiles read.
- The Inbox status labels (finding 21) are shown with **mocked** REST rows: Playground has no IMAP mailbox, so the real Inbox cannot be populated. The measurements are of the real rendered component, the rows are invented.
- Screen reader behaviour, real GSC data, a running Worker, FluentForms claims and the Run now / Resend actions were not exercised (no writes were made against the actions).
- The red "Sitemap or llms.txt is not answering ... rewrite rule is missing" banner may be a Playground artefact (rewrite rules not flushed). I could not check it on a real host. Finding 08 is about how it is shown, not whether the rule is truly missing.
- Console: one `502 (Bad Gateway)` "Failed to load resource" appeared once on the very first page load of a long-lived tab. It did not reproduce in three fresh tabs (Kits Home, InsightWeb Dashboard, SourceWeb Workers, RankWeb Modules: only `JQMIGRATE` log lines). No finding is raised for it.

## 2. Summary

About 35 route and state combinations were opened (section 1); that is not full coverage (see the "not opened" list). Counts: **22 findings**: 1 critical, 12 major, 3 accessibility, 6 notes. All 22 carry a measurement or a verbatim quote.

Top of the list:

- InsightWeb's top-level menu entry is a dead link when Kits Core is off (01).
- "More from Kits" is not reachable from any menu when Core is on (02).
- With Core on, every plugin screen shows two stacked tab bars that disagree (03).
- Two screens print a health verdict that the table under them contradicts (05, 06).
- No REST failures and no console errors on any screen; contrast passes on every measured Core screen (see What works).

## 3. Findings

### 01 · Critical · InsightWeb menu, Kits Core inactive
The InsightWeb top-level menu item points at a URL that does not exist, and the page it was meant to open returns 403.
Anyone running InsightWeb without Core clicks the plugin name in the sidebar and lands on the public site's home page, not on Search Insights. The working entry is a second submenu item the user has to find. "More from Kits" is listed above "Search Insights".

EVIDENCE:
```
Core off. #toplevel_page_aw-search-insights > a  href='insightweb-more'
InsightWeb submenu order: "More from Kits > insightweb-more | Search Insights > aw-search-insights"
GET /wp-admin/insightweb-more  -> redirected to the front end (title "Kits Suite (full) – Kits Core, the Kits theme ...")
GET /wp-admin/admin.php?page=insightweb-more -> 403 (title "WordPress > Error")
Same check on the other five plugins: planweb-more, rankweb-more, mailweb-more, sourceweb-more, directoryweb-more -> 200 "More from Kits"
```
FIX: register the More page after the main screen (priority above the one that registers `add_menu_page`) so the top-level slug is the Search Insights screen; make `insightweb-more` resolve like the other five. File: `plugins/insightweb/includes/more-from-kits.php:67` (the `admin_menu` priority 99 call under `AW_SI_SLUG`) against `plugins/insightweb/includes/search-insights/admin.php:97-102`.

### 02 · Major · "More from Kits", every plugin, Kits Core active
The new "More from Kits" page cannot be reached from the interface when Core is on, and the six plugin-owned copies answer 403.
The Core copy renders at `page=kits-core-more`, but no menu item, tab, card or link points to it: the Kits submenu is Home, Theme Options, Settings, Tools, Help, and the plugin menus are folded under Plugins. The page also has an empty tab title.

EVIDENCE:
```
Core on. Links containing "More from Kits" or "-more" in the HTML of kits, planweb, aw-seo-plus, mailweb,
aw-search-insights, aw-sourcing-menu, directoryweb: 0 (each fetched and searched)
Plugins submenu: Installed Plugins | Add Plugin | DirectoryWeb | SourceWeb | RankWeb | InsightWeb | MailWeb | PlanWeb
GET page=planweb-more, rankweb-more, mailweb-more, insightweb-more, sourceweb-more, directoryweb-more -> 403 each
GET page=kits-core-more -> 200, <title> " ‹ Kits Suite (full) — WordPress" (no page name), <h1> "More from Kits"
Without Core the entry exists in each plugin's menu (e.g. RankWeb: "... Convert to WebP | More from Kits | Settings").
```
FIX: add a "More from Kits" link to the Kits Home screen and to the folded Plugins submenu (or the shell footer). Give the page a title ("More from Kits"). The plugin-owned 403s are by design (`planweb_more...`: "Kits Core's page is the one page"), but a deep link from a plugin should redirect to `kits-core-more` instead of failing.

### 03 · Major · all React plugin screens, Core active
Every Core screen stacks two navigation bars with the same label and different contents, and RankWeb Settings stacks a third row of chips.
The top bar (WordPress `nav-tab-wrapper`, class `kits-fold-tabs`) lists every screen of the plugin; the bar below it (the shell header) lists five or thirteen. Both are named "Screens". Names and order differ, so the user sees "Overview" and "Dashboard" for one page.

EVIDENCE:
```
RankWeb 1280: nav[aria-label="Screens"].kits-fold-tabs = Overview | Insights | Modules | FAQ | Internal links | SEO CSV | Images |
  Redirect tools | Transport | Convert to WebP | Settings   (11)
              nav[aria-label="Screens"].kits-shell-header__tabs = Dashboard | Insights | Modules | FAQ | Settings   (5)
SourceWeb 1280 order differs between the two bars:
  fold bar:  Sources, Keywords, Rules, AI models, Places, Workers, ...
  shell bar: Sources, Keywords, Rules, Places, AI models, Workers, ...
375: .kits-fold-tabs height 193 px (RankWeb Settings, SourceWeb Workers) / 147 px (DirectoryWeb) of an 812 px viewport, above the notice and the page header.
RankWeb Settings: a third row of 9 pill links (Connected services ... Internal links), 1473 px wide in a 343 px scroller at 375.
```
FIX: render one screen nav. If the fold bar must stay, give it a different `aria-label` ("All RankWeb screens") and the same names and order as the shell bar; hide it at 782 px and below, where the shell tabs are enough.

### 04 · Major · SourceWeb, DirectoryWeb and any 10-plus-tab screen
The shell tab strip overflows silently: at 1280 the last tab is clipped, and at 375 the current tab is off-screen with no scroll cue.
A user does not see "Settings" on SourceWeb at the most common laptop width, and on a phone the page opens with the active tab hidden.

EVIDENCE:
```
SourceWeb Workers 1280: .kits-shell-header__tabs clientWidth 1072, scrollWidth 1112, overflow-x:auto;
  last tab "Settings" left 1241 right 1296, viewport 1280.
375: tab strip ul 1112 px wide in 343 px; current tab "Workers" at 712-768 px inside it, scrollLeft 0.
375: document.documentElement.scrollWidth 511 and window.innerWidth 511 (viewport is 375): the page itself is wider than the screen.
```
FIX: scroll the current tab into view on mount (`scrollIntoView({inline:'center'})`), add a fade or chevron at the clipped edge, and wrap or collapse to a select below 640 px. Find which element widens the layout (the 1112 px `ul` is the only wide node) and give the nav `max-width:100%; contain: inline-size`.

## 4. What works
